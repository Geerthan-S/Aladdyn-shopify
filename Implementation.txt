# Build the Complete Aladdyn Shopify Connector

Build a production-ready standalone Next.js application from scratch in the currently opened folder.

Do not stop after scaffolding or provide only sample code. Implement the application, database migrations, Shopify OAuth flow, data inspector, security controls, tests, documentation, and deployment configuration. Run all available validation checks before finishing.

## 1. Product objective

Create a public Aladdyn Shopify Connector with this complete journey:

```text
Tester opens public Aladdyn link
→ Signs up or logs in
→ Enters Shopify store domain
→ Clicks Connect Shopify
→ Redirected to Shopify authorization/install
→ Approves requested access
→ Returned to Aladdyn callback
→ Connection and access token stored securely
→ Shopify Admin GraphQL API 2026-07 verified
→ Tester sees a complete Shopify Data Inspector
→ Tester can paginate data, reconnect, or disconnect
```

This is a standalone application, not an embedded Shopify Admin application.

## 2. Required technology

Use:

- Current stable Next.js with App Router and TypeScript
- React Server Components where appropriate
- Tailwind CSS for the interface
- Supabase Auth for signup, login, logout, password recovery, and sessions
- Supabase Postgres for application data
- Zod or equivalent runtime validation
- Shopify Admin GraphQL API version `2026-07`
- Node.js runtime for routes using cryptography
- Vitest or the project’s suitable unit-test runner
- Playwright for critical end-to-end coverage if practical
- Vercel-compatible deployment configuration

Use current stable compatible package versions. Before implementation, verify the current official Shopify documentation for OAuth, HMAC calculation, API scopes, API version `2026-07`, privacy webhooks, token revocation, and protected customer data.

Do not expose the Shopify access token, Shopify API secret, Supabase service-role key, or encryption key to browser code.

## 3. Architecture

Use this separation:

```text
Browser
  ├── Supabase user authentication
  ├── Connect-store form
  └── Data Inspector UI
          ↓
Next.js server routes/actions
  ├── Validate authenticated Aladdyn user
  ├── Initiate Shopify OAuth
  ├── Validate callback HMAC and state
  ├── Encrypt/decrypt offline access token
  ├── Call Shopify Admin GraphQL
  ├── Normalize GraphQL errors
  └── Process verified webhooks
          ↓
Supabase Postgres
  ├── Connection metadata
  ├── Encrypted token material
  ├── Single-use OAuth states
  └── Webhook idempotency records
```

Shopify GraphQL requests must only happen on the server.

## 6. Supabase database design

Create a committed SQL migration.

### `shopify_connections`

Recommended columns:

```text
id uuid primary key
user_id uuid not null references auth.users(id)
shop_domain text not null
shopify_shop_id text
shop_name text
status text
api_version text
granted_scopes text[]
installed_at timestamptz
verified_at timestamptz
disconnected_at timestamptz
last_error_code text
last_error_message text
created_at timestamptz
updated_at timestamptz
```

Constraints:

- Unique active ownership for a Shopify store
- A store must not silently become connected to another Aladdyn user
- Validate allowed connection statuses
- Normalize domain before writing

### `shopify_connection_secrets`

Recommended columns:

```text
connection_id uuid primary key
token_ciphertext text not null
token_iv text not null
token_auth_tag text not null
key_version integer not null
created_at timestamptz
updated_at timestamptz
```

This table must never be readable through the browser’s Supabase client.

Encrypt access tokens with AES-256-GCM using a 32-byte environment-provided key. Use a fresh random IV for every encryption. Never hash the access token because it must be recoverable for Shopify requests.

### `shopify_oauth_states`

Recommended columns:

```text
state_hash text primary key
user_id uuid not null
shop_domain text not null
redirect_path text
expires_at timestamptz not null
used_at timestamptz
created_at timestamptz
```

Store a hash of the OAuth state rather than the plaintext state. State values must:

- Be generated with a cryptographically secure random generator
- Expire quickly, preferably in 10 minutes
- Be single-use
- Be tied to the user and normalized shop domain
- Be consumed atomically during callback processing

### `shopify_webhook_receipts`

Store only information needed for idempotency and diagnostics:

```text
webhook_id text primary key
topic text not null
shop_domain text
processed_at timestamptz
status text
error_message text
```

Avoid permanently storing protected customer payloads.

### Row-level security

Enable RLS on all relevant tables.

Users may read only their own non-secret connection metadata. Token material, OAuth states, and webhook receipts must only be accessed by trusted server code.

Never expose the Supabase service-role key in a `NEXT_PUBLIC_` variable.

## 7. Shopify OAuth installation flow

### Install route

`GET /api/shopify/install?shop=...`

The route must:

1. Require an authenticated Supabase user.
2. Normalize and validate the Shopify domain.
3. Check whether the shop is already owned by another user.
4. Generate a secure OAuth state.
5. Store only its hash with user, shop, and expiry.
6. Construct the Shopify authorization URL.
7. Redirect to Shopify.

Use an offline access token. Do not request a per-user online token.

Requested baseline scopes:

```text
read_products
read_inventory
read_locations
read_orders
read_discounts
```

Keep the scope list in one server-side constant.

Do not request write scopes.

### Callback route

`GET /api/shopify/callback`

Process in this order:

1. Read the original callback query parameters.
2. Validate the `shop` domain.
3. Verify Shopify’s callback HMAC with timing-safe comparison.
4. Validate callback timestamp freshness if Shopify supplies one.
5. Hash and locate the OAuth state.
6. Confirm that it is unexpired, unused, and belongs to the expected shop.
7. Atomically consume the state to prevent replay.
8. Exchange the authorization code for an offline access token.
9. Fetch the actual granted scopes.
10. Call Admin GraphQL API `2026-07`.
11. Fetch basic shop identity.
12. Encrypt the access token.
13. Store connection metadata and encrypted token in one safe transaction where possible.
14. Redirect to `/dashboard?connected=1`.

Never include an access token in a URL, redirect, error message, client response, analytics event, or log.

If the callback fails, redirect to a safe UI error page containing a non-sensitive error code.

### HMAC requirements

Implement HMAC exactly according to current official Shopify documentation:

- Exclude the `hmac` parameter
- Preserve the required Shopify parameter encoding rules
- Build the canonical message correctly
- Sign with the Shopify API secret using SHA-256
- Compare decoded byte buffers with `timingSafeEqual`
- Reject missing, malformed, or mismatched HMAC values

Add unit tests using fixed valid and tampered callback examples.

## 9. Shopify GraphQL server client

Create one reusable server-only GraphQL client.

It must:

- Decrypt the token only immediately before use
- Call:

```text
https://{shop}/admin/api/2026-07/graphql.json
```

- Send the token through `X-Shopify-Access-Token`
- Set JSON content type
- Apply a request timeout
- Handle non-2xx responses
- Handle top-level GraphQL errors
- Handle nested `userErrors`
- Capture `extensions.cost.throttleStatus`
- Return typed, normalized results
- Never return request headers or access tokens to the client
- Never log raw GraphQL variables if they might contain personal data

## 12. Reconnect flow

Reconnect must:

- Require authentication
- Use the existing normalized shop domain
- Generate a new state
- Repeat Shopify authorization
- Replace the encrypted token only after successful verification
- Update actual granted scopes
- Preserve the previous valid connection if the new attempt fails
- Mark missing newly configured scopes as requiring reauthorization

## 13. Disconnect flow

Add a confirmation dialog.

On disconnect:

1. Require the authenticated owner.
2. Attempt to revoke Shopify API access using the currently documented Shopify method.
3. If revocation succeeds, remove encrypted token material.
4. Mark metadata as disconnected.
5. If Shopify already revoked the token, still complete local cleanup.
6. If Shopify is temporarily unreachable, show a clear error and offer safe retry.
7. Never expose the token during the process.

Treat uninstall and disconnect as different events but converge them to a non-connected state.

## 14. Webhooks

Implement a raw-body webhook endpoint.

Verify `X-Shopify-Hmac-Sha256` before parsing or processing the payload. Use timing-safe comparison.

Support at minimum:

```text

customers/redact

```

Requirements:

- Verify HMAC from the unmodified request body
- Read and validate Shopify topic, shop domain, and webhook ID headers
- Use webhook ID for idempotency
- Return quickly
- Do not log entire privacy payloads
- Mark connection uninstalled for `app/uninstalled`
- Implement compliant handling for mandatory privacy topics
- Delete or anonymize retained shop data when required
- Remove encrypted tokens when installation is gone
- Document any delayed processing design

Register/configure the mandatory compliance webhooks in the Shopify app configuration, not only at runtime.

## 15. Security requirements

The implementation is incomplete unless all are true:

- Access tokens exist only in encrypted database storage and server memory
- Token encryption uses AES-256-GCM
- Every connection/data action checks authenticated ownership
- OAuth state is random, expiring, shop-bound, user-bound, and single-use
- Callback HMAC is verified before code exchange
- Webhook HMAC is verified against raw body
- Domain validation prevents arbitrary-host requests and SSRF
- Shopify API URLs can only use validated `.myshopify.com` domains
- Sensitive environment variables are never client-exposed
- Logs redact tokens, authorization codes, HMACs, cookies, and personal data
- Errors sent to browsers contain safe codes, not secret details
- RLS prevents cross-user connection access
- No arbitrary GraphQL pass-through endpoint exists
- Rate limiting protects OAuth initiation and data endpoints
- State-changing routes use POST where appropriate
- Security headers are configured
- Production cookies are secure
- React output is not used to render untrusted raw HTML
- Disconnect requires explicit confirmation
- Connection ownership conflicts fail closed
